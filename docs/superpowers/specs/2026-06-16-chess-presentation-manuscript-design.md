# 中国象棋机械臂项目展示文稿设计

日期：2026-06-16  
目标文件：`presentation/Chess_Robot_Project_Showcase.md`

## Summary

本次要写一篇面向项目展示和答辩的 Markdown 文稿，既能直接拆成 PPT 讲稿，也能体现项目复盘深度。文稿需要说明团队为什么选择“中国象棋机械臂仿真系统”这个方向，如何定义边界，如何组织四人并行开发，如何把用户命令转化为机械臂可执行轨迹，以及项目中最能体现专业度的技术亮点、困难和解决思路。

最终文稿不是简单罗列功能，而是讲清楚一个机器人系统从需求、架构、规划、仿真、控制到验证的完整闭环。

## Chosen Approach

采用“答辩可讲 + 复盘有深度”的 AB 混合结构：

1. 开头先展示最终系统能力，快速建立项目完成度。
2. 再回到立项取舍，说明项目聚焦 robotics/control，而不是自动对弈、视觉识别或真实硬件接入。
3. 主体按系统数据流展开，从 `MoveCommand` 到 `ExecutionResult`，突出统一接口和模块边界。
4. 技术深度集中放在 UR5/URDF、坐标映射、IK、碰撞检测、A* 路径规划、Fast/Safe mode、轨迹插值和平滑、误差验证。
5. 复盘章节讲迭代中遇到的问题：接口协同、棋盘状态持续更新、中文记谱、末端姿态一致性、路径连续性、PyBullet 集成和验证输出。
6. 增加“展示增强数据计划”，说明后续将补充更丰富的可视化数据，并规划一个独立测数/出图模块生成答辩素材。
7. 结尾强调项目价值：它不是一个单点 demo，而是一个有分层、有契约、有规划、有验证的仿真机器人系统。

选择这个结构的原因：它既适合课堂展示，能让听众快速听懂系统做了什么；也能体现工程思考，展示团队不是堆功能，而是在做可解释、可验证、可扩展的系统。

## Content Structure

目标文稿建议包含以下章节：

1. 项目概述：一句话说明系统和最终能力。
2. 立项思考与边界：为什么聚焦机械臂任务闭环，哪些范围主动不做。
3. 系统架构：A/B/C/D 四层分工，统一接口和主流程。
4. 从一步棋到机械臂动作：命令解析、棋盘状态、逻辑动作、运动基元、轨迹和执行结果。
5. 仿真与机械臂建模：PyBullet、UR5、URDF、棋盘和棋子建模、虚拟吸附。
6. 运动学与轨迹规划：棋盘坐标映射、IK、末端姿态、safe height。
7. 避障与安全策略：障碍物建模、碰撞检测、占据栅格、A* 路径搜索、路径平滑、人手安全区、Fast/Safe mode。
8. 控制执行与结果验证：关节轨迹执行、FK/EE 误差、obstacle clearance、CSV 和曲线。
9. 迭代中的困难与解决：按问题-分析-方案-结果组织。
10. 展示增强数据计划：列出计划补充的可视化数据，包括路径长度、规划时间、轨迹平滑度、速度模式占比、最小避障距离分布、关节误差统计、末端轨迹对比等。
11. 新测数模块规划：建议新增 `scripts/collect_presentation_metrics.py` 或同类脚本，统一运行展示场景、导出 CSV/PNG/summary，用于后续 PPT 和答辩材料。
12. 展示场景建议：普通走子、吃子、绕障、hand_on/hand_off、reset、结果图。
13. 总结与可扩展方向：从仿真验证走向更强规划后端、真实硬件或更完整交互。

## Writing Boundaries

文稿必须保持以下口径：

- 不讨论项目开发中使用的辅助工具或生成过程。
- 避障叙事以当前规划模块能力为准：障碍物建模、碰撞检测、占据栅格、A* 路径搜索、路径插值、平滑和可视化验证。
- 不暴露演示脚本中的实现取舍为项目弱点。
- 不夸大为真实硬件系统；明确这是 simulation validation。
- 不承诺完整象棋裁判、胜负判断、视觉识别或真实夹爪动力学。
- 不把文稿写成代码说明书；代码名只在帮助解释架构和数据流时使用。
- 计划中的新可视化数据或新测数模块必须以“计划补充/建议实现”的口径呈现，不能写成已经完成的结果。

## Tone

整体语气应专业、清晰、有项目推进感。可以有“我们为什么这样做”的思考，但不要写成流水账。每个技术亮点都尽量回答三个问题：

1. 遇到了什么真实问题？
2. 我们为什么选择这个方案？
3. 这个方案如何在系统里落地并被验证？

## Open Risks

- 现有结果数据中部分数值可能来自 mock 或仿真驱动混合流程，正文需要强调“仿真验证与曲线输出”，避免过度承诺真实硬件精度。
- 文稿需要从已有代码和文档提炼，不应引入没有证据支撑的新功能。
- 对尚未生成的新可视化数据，应列为后续展示增强计划，避免和现有验证结果混淆。
- `docs/项目大纲project_outline.md` 当前有未提交改动，写作时只读取内容，不覆盖该文件。

## Acceptance Criteria

最终交付应满足：

- 在 `presentation/` 下新增一篇完整 Markdown 文稿。
- 文稿覆盖立项过程、思考过程、技术栈亮点、困难与解决思路、最终展示建议。
- 文稿可直接作为答辩/PPT 的内容底稿。
- 文稿包含一节新的可视化数据增强计划，并可列出新测数/出图模块的职责、输入输出和建议产物。
- 文稿不包含与写作边界冲突的表述。
- 文稿引用项目中真实存在的模块、文档、测试和结果产物作为叙事依据。
